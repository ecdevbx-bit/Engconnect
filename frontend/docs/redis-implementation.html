📌 What is Redis & Why English Connection Uses It

What is Redis?

Redis stands for Remote Dictionary Server. It is an in-memory data structure store that operates as a cache and session store. Unlike a traditional database (like MariaDB), Redis keeps all data in RAM for extremely fast access (microseconds vs milliseconds).

Key Difference:
  • MariaDB: Persistent disk storage, slower queries, best for complex relationships
  • Redis: Volatile memory storage, ultra-fast access, best for temporary state and caching

Why English Connection Uses Redis

Use Case Reason Benefit
Game Sessions Jumble Words state is temporary (2h lifetime) Sub-millisecond read/write, auto-expiring data

🏗️ Architecture & Data Flow

Game Session Lifecycle

User starts Jumble Words game ↓ Frontend: POST /api/game/jumble-words/start ↓ Backend: GameSessionService creates GameSession object ↓ Backend: GameSessionRedisService.save(session) → Redis ↓ Redis: Key=game_session:UUID, Value=GameSession JSON, TTL=2h ↓ User submits answer → Redis lookup (fast, no DB hit) ↓ Session complete → Delete from Redis (or auto-expire after 2h) ↓ Backend: Persist final score to MariaDB (UserXP table)

XP Event Processing Flow

User answers question correctly ↓ Backend: Emit XP event to Redis stream ↓ Async processor: Reads from xp_events stream ↓ Calculate XP reward (based on difficulty) ↓ Update user.totalXp in MariaDB ↓ Mark xp_processed:{userId}_{sessionId}_{position}=true ↓ Frontend: Poll /api/auth/sync → Get updated XP

Two-Tier Storage Architecture

Layer 1: Redis (In-Memory, Fast)
  • Game sessions (temporary, 2h)
  • XP event queue
  • Content counters
  • Session state during active play
Layer 2: MariaDB (Persistent, Reliable)
  • User profiles
  • Historical game records
  • Final XP tallies
  • User authentication data

💻 Implementation Deep Dive

Spring Boot Redis Configuration

File: RedisConfig.java

@Configuration
public class RedisConfig {
    @Bean
    public RedisTemplate<String, Object> redisTemplate(
            RedisConnectionFactory connectionFactory) {

        // Setup ObjectMapper with LocalDateTime support
        ObjectMapper redisMapper = new ObjectMapper();
        redisMapper.registerModule(new JavaTimeModule());
        redisMapper.disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS);

        // Enable polymorphic deserialization
        redisMapper.activateDefaultTyping(
            redisMapper.getPolymorphicTypeValidator(),
            ObjectMapper.DefaultTyping.NON_FINAL
        );

        // Create JSON serializer
        GenericJackson2JsonRedisSerializer jsonSerializer =
            new GenericJackson2JsonRedisSerializer(redisMapper);

        // Configure Redis template
        RedisTemplate<String, Object> template = new RedisTemplate<>();
        template.setConnectionFactory(connectionFactory);
        template.setKeySerializer(new StringRedisSerializer());
        template.setValueSerializer(jsonSerializer);

        return template;
    }
}
Key Points:
  • StringRedisSerializer for keys (human-readable)
  • GenericJackson2JsonRedisSerializer for values (complex objects)
  • JavaTimeModule to handle LocalDateTime serialization
  • DefaultTyping.NON_FINAL for polymorphic deserialization

Game Session Redis Service

File: GameSessionRedisService.java

@Service
public class GameSessionRedisService {

    private static final String KEY_PREFIX = "game_session:";
    private static final Duration SESSION_TTL = Duration.ofHours(2);

    private final RedisTemplate<String, Object> redisTemplate;

    // Save session with 2-hour expiry
    public void save(GameSession session) {
        String key = buildKey(session.getSessionId());
        redisTemplate.opsForValue().set(key, session, SESSION_TTL);
    }

    // Retrieve session (returns empty if expired/not found)
    public Optional<GameSession> findById(String sessionId) {
        String key = buildKey(sessionId);
        Object value = redisTemplate.opsForValue().get(key);
        return Optional.ofNullable((GameSession) value);
    }

    // Update status without losing TTL
    public void updateStatus(String sessionId, GameSessionStatus status) {
        Optional<GameSession> sessionOpt = findById(sessionId);
        if (sessionOpt.isPresent()) {
            GameSession session = sessionOpt.get();
            session.setStatus(status);

            // Preserve remaining TTL
            Long remainingTtl = redisTemplate.getExpire(buildKey(sessionId));
            Duration ttl = (remainingTtl != null && remainingTtl > 0)
                ? Duration.ofSeconds(remainingTtl)
                : SESSION_TTL;

            redisTemplate.opsForValue().set(buildKey(sessionId), session, ttl);
        }
    }

    // Delete session manually
    public void delete(String sessionId) {
        redisTemplate.delete(buildKey(sessionId));
    }
}

        return ApiResponse.success("Answer submitted", submitData);
    }

🎓 Essential Concepts to Study

1. In-Memory Data Structure Store

What: Redis stores data in RAM, not disk.

Why it matters: Allows microsecond-level access, but data is lost if server crashes.

Study: How RAM differs from disk storage, trade-offs, persistence options (RDB, AOF).

2. Key-Value Abstraction

What: Redis is fundamentally a dictionary/map: every value is accessed by a unique key.

Pattern in English Connection: game_session:{UUID}, content_count:{DIFFICULTY}

Study: How to design key hierarchies (namespacing), collision prevention, naming conventions.

3. Data Type Variety

Redis is NOT just strings—it has rich native types:

  • Strings: Binary-safe, can store JSON, serialized objects
  • Lists: Ordered sequences, great for queues
  • Sets: Unordered unique values, great for membership checks
  • Hashes: Maps within Redis, efficient for structured data
  • Sorted Sets: Ordered by score, great for leaderboards
  • Streams: Log-like data structure, great for event queues

English Connection uses: Strings (content counts), Serialized objects (sessions), Streams (XP events)

4. TTL & Expiration

What: Keys can have a time-to-live (TTL). After TTL seconds, the key auto-deletes.

Example: Game session expires after 2 hours with no manual cleanup needed.

Study: EXPIRE command, TTL strategies, eviction policies, handling expiry edges.

5. Serialization & Deserialization

What: Converting Java objects ↔ Redis strings (usually JSON).

English Connection: Uses Jackson with Spring Data Redis to auto-serialize GameSession to JSON.

Study: JSON serialization, Jackson annotations (@JsonProperty, @JsonIgnore), version compatibility.

6. Connection Pooling

What: Reusing TCP connections to Redis instead of opening new ones each time.

English Connection: Spring Data Redis handles this automatically via RedisConnectionFactory.

Study: Lettuce/Jedis drivers, connection pools, timeout configuration.

7. Atomicity & Transactions

What: Redis commands are atomic (execute fully or not at all).

Limitation: Multi-command transactions require MULTI/EXEC (more complex).

Study: When single commands are sufficient vs multi-command transactions, watch/unwatch.

8. Cache Invalidation

Pattern: "There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton

English Connection: TTL handles session cleanup, but content counters need manual updates on data changes.

Study: Invalidation strategies: TTL, manual delete, event-driven, cache-aside patterns.

9. Spring Data Redis Abstraction

What: Spring's wrapper around Redis drivers (Jedis, Lettuce).

Provides: RedisTemplate, repository pattern, automatic serialization, connection management.

Study: RedisTemplate operations (opsForValue, opsForHash, opsForList), Spring caching annotations.

10. Concurrency & Thread Safety

What: Multiple threads accessing Redis simultaneously.

English Connection: Spring Data Redis is thread-safe; RedisTemplate can be shared.

Study: Thread-safe operations, Lua scripting for complex multi-step operations, optimistic locking.

🎯 Design Patterns Used

1. Service Layer Pattern

GameSessionRedisService encapsulates all Redis operations. Controllers don't know Redis details.

Controller → Service (Redis) → Data
                    ↓
            Service abstracts Redis API

2. Repository Pattern

Methods like findById(), save(), delete() mimic database repository interface.

Benefit: Easy to swap Redis for another store (e.g., Memcached, database cache).

3. Optional Pattern

public Optional<GameSession> findById(String sessionId) { ... }
// Caller:
gameSessionRedisService.findById(id)
    .orElseThrow(() -> new AppException(SESSION_NOT_FOUND));

Benefit: Explicit handling of "not found" cases, avoids null pointer exceptions.

4. TTL Pattern

Automatic cleanup via Redis expiration instead of manual deletion or scheduled jobs.

Benefit: Distributed cleanup, no garbage collector needed, reduces storage over time.

5. Cache-Aside Pattern

// Check cache first
GameSession session = redis.get(sessionId);

// If miss, compute and store
if (session == null) {
    session = computeOrFetch();
    redis.set(sessionId, session, TTL_2_HOURS);
}

6. Prefix Pattern (Namespacing)

Use prefixes to organize keys: game_session:*, content_count:*, xp_processed:*

Benefit: Clear semantics, easy to scan/delete related keys, prevents collisions.

7. Event-Driven Async Pattern

XP events are queued in Redis → async processor handles them → updates MariaDB.

Benefit: Decouples user action from slow database write, improves responsiveness.

⚠️ Things to Watch Out For

1. Data Loss Risk
Redis data is lost on server crash unless RDB/AOF persistence is enabled.
Mitigation: For critical data, always have a persistent store (MariaDB) and use Redis as cache only.
2. Memory Limits
If Redis memory is exhausted, eviction policies kick in (may delete important data).
Mitigation: Monitor memory usage, set maxmemory policy, use TTLs aggressively.
3. Serialization Overhead
Complex objects (GameSession with 6 sentences) are large when JSON serialized.
Mitigation: Consider storing only essential fields, or use MessagePack for compression.
4. Cache Invalidation
If content_count:EASY is stale (not updated after adding sentences), load-balancing breaks.
Mitigation: Invalidate cache whenever underlying data changes, or use event-driven updates.
5. Single Node Risk
Single Redis instance is a single point of failure.
Mitigation (Future): Set up Redis Sentinel or Cluster for HA.

🚀 Performance Optimization Tips

  • Pipeline: Batch multiple commands in one round-trip (e.g., get 10 counters at once)
  • Pub/Sub: Use Redis streams/pub-sub for real-time updates instead of polling
  • Lua Scripts: For complex multi-step operations, use Lua to execute atomically on Redis
  • Compression: For large objects, compress before storing (brotli, gzip)
  • Monitor: Use redis-cli MONITOR to see commands in real-time for debugging

Expiration

redis-cli TTL "game_session:abc"                # Check remaining TTL
redis-cli PEXPIRE key 5000          # TTL in milliseconds

Inspection

redis-cli TYPE "content_count:EASY"     # Check data type
redis-cli MEMORY USAGE key          # Bytes used by key
redis-cli OBJECT ENCODING key       # Internal encoding

Monitoring

redis-cli MONITOR                       # Watch all commands
redis-cli SLOWLOG GET 10            # Last 10 slow commands
redis-cli CLIENT LIST               # Connected clients
